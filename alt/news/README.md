# ข่าวสารจากทีมพัฒนา

ประกาศถึงผู้ใช้ (ฟีเจอร์ใหม่ · ธีมใหม่ · อัปเดตแอป) ที่ขึ้นในจอ **"ข่าวสาร"** ของแอป
(แท็บ "ฉัน" → ข่าวสารจากทีม) — **แยกจากการแจ้งเตือนงานโดยตั้งใจ**: ไม่นับบนกระดิ่ง ไม่ขึ้นหน้าแรก
เพราะข่าวจากทีมไม่ได้ขอให้นักเรียนตัดสินใจอะไร

| ไฟล์ | คืออะไร | แอปโหลดไหม |
|---|---|---|
| `announcements.json` | ประกาศที่ผู้ใช้เห็นจริง | โหลด (`news.js`) |
| `drafts.json` | ร่างที่ AI เสนอ รอเจ้าของอนุมัติ | ไม่โหลด — ยกเว้นเปิดแอปด้วย `?newsDraft=1` เพื่อดูหน้าตาจริงก่อนอนุมัติ |
| `../devtools/news.mjs` | ตัวรวมหลักฐาน + ตัวตรวจ | ไม่โหลด |
| `../news.js` | จอข่าวสารในแอป | โหลด |

เพิ่มประกาศ **ไม่ต้องขึ้นเลขรุ่นแอป** — แก้ JSON แล้ว push ผู้ใช้ก็เห็นเลย (service worker ดึงไฟล์แบบ network-first)

---

## ขั้นตอน (AI ทำ 1–4 · เจ้าของทำ 5)

1. **รวมหลักฐาน** ของรุ่นที่จะประกาศ
   ```
   node alt/devtools/news.mjs evidence 1C57 > หลักฐาน.md
   ```
   ได้: แพตช์โน้ตของรุ่น · คอมมิตในช่วงรุ่น · ไฟล์ที่เปลี่ยน · บรรทัดที่บอกว่า "ยังไม่ …"
2. **อ่านแล้วคัด** — ประกาศเฉพาะสิ่งที่ผู้ใช้ *เห็นหรือใช้ได้แล้ว* บนเว็บจริง
3. **ร่างลง `drafts.json`** ภาษาไทยที่นักเรียน ม.ต้นอ่านรู้เรื่อง (ดูกติกาข้างล่าง)
4. **ตรวจ** — ต้องผ่านก่อนส่งให้เจ้าของดู
   ```
   node alt/devtools/news.mjs check
   ```
5. **เจ้าของอนุมัติ** — เปิด `/alt/?newsDraft=1` ดูหน้าตาจริง → ย้ายชิ้นที่อนุมัติจาก `drafts.json`
   ไป `announcements.json` → `check` อีกรอบ → commit → push (push = ขึ้นเว็บจริงทันที)

## กติกาเนื้อหา — ห้ามแต่ง

- **ทุกช่องที่ผู้ใช้อ่าน** (`title` · `body` · ทุกข้อใน `points`) ต้องมี `evidence` อย่างน้อยหนึ่งชิ้น
  ที่ `for` ชี้มาที่ช่องนั้น และ `quote` ต้องยกมา **ตรงตัว** จาก
  - `"patchnotes"` = แพตช์โน้ตของรุ่นใน `release` เท่านั้น (ยกข้ามรุ่นไม่ได้) หรือ
  - `"commit:<sha>"` = ข้อความคอมมิตนั้น
  ตัวตรวจเทียบแบบไม่สนตัวหนา/backtick/ช่องว่าง แต่คำต้องตรง
- **ห้ามประกาศ** ของที่แพตช์โน้ตบอกว่า "ยังไม่ได้รัน / ยังไม่เปิด / รอเจ้าของ / ยังค้าง"
  ตัวอย่างจริงจาก 1C57: เมนูแชท "ตอบกลับ · แก้ไข · ปักหมุด · ปฏิกิริยา" ต้องรันไฟล์ฐานข้อมูลก่อน
  และแพตช์โน้ตบอกว่ายังไม่ได้รัน → ประกาศได้แค่ คัดลอก · ส่งต่อ · ยกเลิกการส่ง
- **ห้ามคำสัญญาอนาคต** — "เร็ว ๆ นี้" "กำลังจะมา" "เตรียมพบ" "ในอนาคต" ฯลฯ ตัวตรวจไม่ให้ผ่าน
- **ห้ามพูดชื่อไฟล์ ชื่อฟังก์ชัน ชื่อไลบรารี** (React Bits · Supabase · `inbox.js`) — ผู้ใช้ไม่รู้จัก
- **บอกผลที่ผู้ใช้ได้** ไม่ใช่สิ่งที่ทีมทำ: "กดแล้วเปิดงานชิ้นนั้นเลย" ไม่ใช่ "ปรับปรุงระบบนำทาง"
- ไม่มีอิโมจิท้ายประโยค ไม่มีตัวเลขเปอร์เซ็นต์ลอย ๆ ที่ไม่ได้วัด
- **ตัวตรวจเช็คได้ว่าคำพูดมีจริง แต่เช็คไม่ได้ว่าประโยคไทยที่เขียนใหม่ "แปลว่าอย่างเดียวกัน"**
  — ด่านนั้นคือเจ้าของในขั้นที่ 5 · ร่างทุกชิ้นจึงต้องเขียนให้เทียบกับคำพูดที่ยกมาได้ง่าย

## รูปแบบหนึ่งประกาศ

```json
{
  "id": "1c57-room-lamp-switch",
  "date": "2026-10-15",
  "release": "1C57",
  "kind": "feature",
  "title": "ห้องของฉัน: กดเปิดปิดไฟเองได้",
  "body": "ป้ายไฟในห้องของฉันกลายเป็นสวิตช์ ...",
  "points": ["...", "..."],
  "action": { "label": "ไปห้องของฉัน", "screen": "scr-room" },
  "evidence": [
    { "for": ["title", "body"], "source": "patchnotes", "quote": "ป้ายไฟในห้อง = สวิตช์ไฟ" },
    { "for": "points.0", "source": "commit:674ed15", "quote": "..." }
  ]
}
```

| ช่อง | กติกา |
|---|---|
| `id` | a-z 0-9 - · ห้ามซ้ำ · ห้ามเปลี่ยนหลังเผยแพร่ (แอปจำว่าอ่านแล้วด้วย id) |
| `date` | YYYY-MM-DD วันที่ของนั้นขึ้นเว็บ · ห้ามอยู่ในอนาคต |
| `release` | เลขรุ่นที่มีหัว `# StudentOS Update <เลข>` ใน PATCHNOTES.md |
| `kind` | `feature` ฟีเจอร์ใหม่ · `theme` ธีมใหม่ · `update` อัปเดตแอป · `fix` แก้ไข |
| `title` | 4–60 ตัวอักษร |
| `body` | ไม่เกิน 280 ตัวอักษร |
| `points` | ไม่บังคับ · ไม่เกิน 5 ข้อ ข้อละไม่เกิน 120 |
| `action` | ไม่บังคับ · `screen` ต้องอยู่ใน `NEWS_OPEN` ของ `news.js` (จอที่ `go()` วาดเองได้) |

ประกาศที่ใหม่กว่า 30 วันและยังไม่เปิดดู นับเป็นเลขบนแถว "ข่าวสารจากทีม" ในแท็บฉัน
