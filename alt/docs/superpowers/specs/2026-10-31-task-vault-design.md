## 1. ทำไมต้องมี

เทสเตอร์ขอ "ที่เก็บงานแบบ Notion" — ถ่ายใบงาน/โจทย์ครั้งเดียวแล้วเปิดดูได้ตอนทำ เก็บงานที่ทำเสร็จไว้ทวนก่อนสอบ
เจ้าของสั่ง: "ปรับให้มันเก็บข้อมูลได้ด้วยนะ" → ลองต้นแบบแล้ว → "ลองเอาไปใส่ในปุ่มหน่อย"

ข้อกำหนดจากเจ้าของ (คำตอบตรง ๆ):

| เรื่อง | เจ้าของเลือก |
|---|---|
| เก็บรูปที่ไหน | **ขึ้นคลาวด์ตั้งแต่แรก** (ไม่ใช่เก็บในเครื่องก่อน) |
| ทางเข้า | **แท็บ "ฉัน"** + **ไทล์หน้าแรก** |
| ไทล์หน้าแรกเต็ม 3×2 แล้ว | **"คลังงาน" แทน "สถิติ"** (สถิติยังเข้าได้จากแท็บ "ฉัน") |
| สาย | ทั้งแอปหลักและ ALT |

ผ่านกฎวิสัยทัศน์ไหม: คลังงานไม่ได้ตัดสินใจแทน แต่ **ลดของที่ต้องหา** ตอนลงมือทำ (โจทย์อยู่ในโหมดโฟกัส ไม่ต้องออกไปหาในแกลเลอรี)
ส่วนที่เป็น "ที่เก็บ" อยู่หลังแท็บ "ฉัน" ตามกฎ · ไทล์หน้าแรกเจ้าของเลือกเองโดยรู้ว่าแทนของเดิม จำนวนไทล์ไม่เพิ่ม

**วัดว่าได้ผล:** สัดส่วนงานที่มีรูปโจทย์ · สัดส่วนรอบโฟกัสที่กด "ดูโจทย์" (นับในเครื่อง ไม่ส่งรูปไปไหน)

## 2. หน้าจอ (ตามต้นแบบที่ลองแล้ว)

1. **ทางเข้า**
   - ไทล์ "คลังงาน" ในกริดหน้าแรก ตำแหน่งเดิมของ "สถิติ" (แถวล่างใบแรก) · ไอคอน Lucide `archive` (ISC)
   - แถว "คลังงาน" ในลิสต์ทางเข้าของแท็บ "ฉัน" · บรรทัดรอง "N รูป · M งาน"
   - ทั้งสองทางผูกชื่อฟีเจอร์ `vault` ใน Feature Manager (`sosFeature`) — ปิดฟีเจอร์ = ทุกทางเข้าหาย
2. **จอคลัง (`scr-vault`)** — โฟลเดอร์ตามวิชา (สีวิชาเดิมของแอป) · แตะโฟลเดอร์ = กรอง · รายการงาน:
   งานที่มีรูป/โน้ตขึ้นก่อน → ที่เหลือเรียงตามกำหนดส่ง · งานที่ส่งแล้วยังอยู่ (ป้าย "ส่งแล้ว ✓" สีเขียว ไม่ใช่สีทอง — ทองไว้ของสำเร็จจริงเท่านั้น และ "มีรูป" ไม่ใช่ความสำเร็จ)
   ล่างสุด: ใช้พื้นที่ไปเท่าไหร่จากเพดาน (ข้อ 5)
   คลังว่าง = ภาพแบบ Cult UI Fluid Rendering จากม็อกอัปจอ 5
3. **หน้างาน (`scr-vault-task`)** — หัวการ์ดงาน + เส้นสายสี่สาย (Cult UI Illustration Fluid Rendering · MIT) เข้าสี่กลุ่ม:
   โจทย์ · ใบงาน (`q`) · งานที่ทำเสร็จ (`done`) · โน้ต · สไลด์ (`note`) · จดไว้ (ข้อความ)
   "+ เพิ่ม" → เลือกได้หลายรูปทีเดียว (หรือถ่ายต่อกัน) → แผ่นยืนยันเลือกประเภททั้งชุด → บันทึก
   แตะรูป = ดูเต็มจอ ปัดซ้ายขวา · ลบ = แตะสองครั้ง (ปุ่มแดง "แตะอีกครั้งเพื่อลบ" ไม่มีกล่องถาม)
   ปุ่มหลัก "เริ่มทำ" = `startFocus(id)` ตัวเดิม
   (ทางเข้ามีแค่สองทางตามที่เจ้าของเลือก — ไม่เพิ่มปุ่มในแผ่นแก้ไขงาน · ถ้าใช้แล้วหาไม่เจอค่อยคุยกันใหม่)
4. **โหมดโฟกัส** — งานมีรูปโจทย์ = แถว "ดูโจทย์" (รูปแรก + จำนวน) → ดูเต็มจอทับโหมดโฟกัส ไม่หยุดเวลา
   ไม่มีรูป = จอเหมือนเดิมทุกพิกเซล
   กด "เสร็จแล้ว" ในงานที่ยังไม่มีรูปกลุ่ม `done` → จอ "เสร็จแล้ว" เดิมได้ปุ่มรอง "ถ่ายงานที่ทำเสร็จ" (ไม่บังคับ · ไม่แทรกก่อน "งานถัดไป")

**หน้าแรกต้องไม่ต้องเลื่อนที่ 375×812** — แทนไทล์ ไม่เพิ่ม จึงสูงเท่าเดิม · วัดซ้ำทุกธีมหลังทำ

## 3. ข้อมูล

### 3.1 รายการรูปกับโน้ต อยู่ในงาน (ซิงก์ด้วยระบบเดิม)

```js
t.note  = 'ข้อ 7 ถามครูก่อน'                // "จดไว้" · ช่องค้นหางาน (matchTask) ค้นช่องนี้อยู่แล้ว
t.files = [{ id: 'f…', kind: 'q'|'done'|'note', w: 1200, h: 1600, bytes: 241000, at: 1793…, up: true }]
```

- ไม่มี `t.files` = ไม่มีรูป (ไม่ต้องย้ายข้อมูลเก่า)
- `up: false` = ยังไม่ขึ้นคลาวด์ (ไฟล์อยู่ในเครื่องรอส่ง)
- ซิงก์ ย้ายตามบัญชีตอนสลับ (`stashAccount`/`swapInAccount`) และรวมสามทาง (`syncMergeById`) ได้ฟรี เพราะเป็นส่วนหนึ่งของงาน

**ทำไมไม่ทำตารางใหม่:** ตารางต้องมี RLS · โหลดแยก · รวมข้ามเครื่องแยก · ย้ายตอนสลับบัญชีแยก — ทั้งหมดนี้งานมีอยู่แล้ว
**ราคาที่จ่าย:** สองเครื่องเพิ่มรูปลงงานเดียวกันในช่วงซิงก์เดียวกัน → งานถูกรวมแบบ "เครื่องที่แก้ล่าสุดชนะ" (กติกาเดิมของ `syncMergeById`)
รายการรูปของเครื่องหนึ่งหาย · ไฟล์ยังอยู่บนคลาวด์และถูกเก็บกวาด (3.5) — เกิดยากมาก (ต้องแก้งานเดียวกันพร้อมกันสองเครื่อง) ยอมรับได้

### 3.2 ไฟล์รูป: Supabase Storage bucket `task-files` (ปิด)

- path `<uid>/<fileId>.jpg` · `public = false` · `file_size_limit = 1048576` · `allowed_mime_types = {image/jpeg}`
- policy บน `storage.objects` สามข้อ แบบเดียวกับ bucket `dm`: insert / select / delete เฉพาะ `(storage.foldername(name))[1] = auth.uid()::text`
  ไม่มี update (รูปแก้ไม่ได้ ลบแล้วเพิ่มใหม่) · ไม่มีใครอ่านของคนอื่นได้ รวมถึงเพื่อน
- อ่านด้วย `createSignedUrl(path, 3600)` (ลอกจาก `social.js` ของ `dm`)
- migration ใหม่ `supabase/migrations/20261031120000_task_files.sql` — **เจ้าของเป็นคนรัน** (ไม่มีทางอื่นสร้าง bucket จาก repo)

### 3.3 ที่พักในเครื่อง: IndexedDB `studentos-files`

store `blobs` · key = `fileId` · ค่า `{ owner, blob, at, pending }`
- เป็นทั้งแคช (เปิดดูซ้ำไม่ต้องโหลดใหม่ · ออฟไลน์ดูได้) และคิวส่ง (`pending: true`)
- `owner` = uid หรือ `'guest'` — อ่าน/แสดงเฉพาะของ owner ปัจจุบัน สลับบัญชีแล้วไม่เห็นรูปของอีกคน
- ขอ `navigator.storage.persist()` ครั้งแรกที่เก็บรูป (ลดโอกาสเบราว์เซอร์ล้างเอง)
- **ห้ามแตะคีย์ `studentos.alt.*`** — ไฟล์ไม่เข้า localStorage เลย

### 3.4 ย่อรูป

canvas ด้านยาวไม่เกิน 1600px → JPEG 0.82 (เท่าต้นแบบ · ใบงานจริงได้ ~200–400KB) · เกิน 1MB หลังย่อ = ลดคุณภาพเหลือ 0.7 แล้วลองอีกครั้ง

### 3.5 ทางเดินของข้อมูล

| เหตุการณ์ | ทำอะไร |
|---|---|
| เพิ่มรูป | ย่อ → IndexedDB (`pending`) → `t.files` เพิ่ม `up:false` → `save()` → ส่งขึ้น `task-files` → สำเร็จ = `up:true` + `save()` |
| ออฟไลน์ / ส่งพลาด / ยังไม่ล็อกอิน | ค้าง `up:false` · ส่งซ้ำตอน: เปิดแอป · กลับมาออนไลน์ · ล็อกอิน · เพิ่มรูปใหม่ · ส่งทีละรูป ไม่พร้อมกัน |
| เปิดดูรูป | มีใน IndexedDB = ใช้เลย · ไม่มี + `up:true` = signed URL → โหลด → เก็บแคช · ไม่มีทั้งคู่ = ช่องรูปเทาพร้อมป้าย "โหลดไม่ได้" ไม่ล้ม |
| ลบรูป | ออกจาก `t.files` + IndexedDB ทันที → ลบบนคลาวด์ · ลบบนคลาวด์ไม่ได้ (ออฟไลน์) = จดไว้ในคิวลบ ลองใหม่รอบส่งถัดไป |
| ย้ายงานลงถังขยะ | ไม่แตะรูป (กู้งานคืน = รูปกลับมาครบ) |
| ลบงานถาวร (`deleteForever` · `emptyBin` · `purgeOldTrash`) | ลบรูปทุกใบของงานนั้น (ทางเดียวกับ "ลบรูป") |
| เก็บกวาด (วันละครั้ง ตอนเปิดแอป · ล็อกอินอยู่) | ลิสต์ `<uid>/` บนคลาวด์ → ลบไฟล์ที่ไม่มีงานไหน (รวมในถัง) อ้างถึง **และ** เก่ากว่า 1 วัน (กันลบของที่อีกเครื่องเพิ่งอัปโหลดแต่ยังไม่ซิงก์งานมา) |
| ใช้แบบไม่ล็อกอินแล้วล็อกอิน (`adoptAccountIfNeeded` → `'same'`) | IndexedDB เปลี่ยน owner `'guest'` → uid · งานตามขึ้นบัญชีอยู่แล้ว → ส่งรูปที่ค้าง |
| สลับบัญชี | ไม่ต้องย้ายไฟล์ — `t.files` ไปกับ state ของแต่ละบัญชี · IndexedDB กรองด้วย owner |
| ลบบัญชี | **ก่อน** เรียก `delete_account()`: ลิสต์แล้วลบ `<uid>/` ทั้งโฟลเดอร์ใน `task-files` · ลบไม่หมด = ยังลบบัญชีต่อ แต่บอกผู้ใช้ตรง ๆ ว่ารูปบางส่วนค้าง (ไม่ปิดบัง) · ล้าง IndexedDB ของ owner นี้ |

## 4. ส่วนของเซิร์ฟเวอร์

- migration ข้อ 3.2 อย่างเดียว · ไม่มี Edge Function ใหม่ · ไม่มีตารางใหม่
- ไม่มีกุญแจหรือความลับลง repo
- ช่องโหว่ที่เจอระหว่างออกแบบ (ไม่ได้แก้ในงานนี้ · แจ้งเจ้าของ): `delete_account()` ไม่ลบไฟล์ใน bucket `posts`/`dm` ของคนที่ลบบัญชี

## 5. เพดาน

| อะไร | เท่าไหร่ | เพราะ |
|---|---|---|
| ต่อรูป | 1MB (bucket บังคับ) | หลังย่อแทบไม่มีรูปไหนเกิน |
| ต่อบัญชี | **300 รูป** (~75MB) | Supabase แผนฟรีมีพื้นที่รวม 1GB · 300 รูป ≈ งานทั้งเทอมที่ถ่ายงานละ 2–3 รูป · ครบเพดาน = ปุ่มเพิ่มบอก "คลังเต็ม ลบรูปเก่าก่อน" |

**ตัวเลข 300 เป็นค่าตั้งต้น เจ้าของเปลี่ยนได้** (ค่าคงที่ตัวเดียวใน app.js)

## 6. ไม่ทำในรอบนี้

แชร์รูปให้เพื่อน · อ่านตัวหนังสือจากรูปในคลัง (OCR) · PDF/ไฟล์อื่น · ครอป/หมุนรูป · ค้นหาในคลัง ·
ถ่ายหลายรูปในจอเพิ่มงานด้วย OCR (เป็นงานแยกที่ยังรอเจ้าของตอบอยู่)

## 8. ความเสี่ยงที่ยอมรับ

- **iPhone ที่เปิดผ่าน Safari แบบไม่ติดตั้ง** ล้าง IndexedDB เองถ้าไม่ได้เปิดเว็บ 7 วัน — รูปที่ขึ้นคลาวด์แล้วไม่หาย (โหลดใหม่ได้) · รูปที่ยังไม่ได้ส่ง (ออฟไลน์ตลอด 7 วัน) หายได้
- พื้นที่ Supabase แผนฟรี 1GB รวมทุกคน — 300 รูปต่อคน รับได้ราว 13 คนที่ใช้เต็มเพดาน · ก่อนเปิดให้คนจำนวนมากใช้ต้องดูราคาอีกที
- แก้งานเดียวกันพร้อมกันสองเครื่อง = รายการรูปของเครื่องหนึ่งหาย (ข้อ 3.1)
