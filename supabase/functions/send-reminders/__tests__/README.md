# เทสต์ของ send-reminders

รันบน **Node ธรรมดา** ไม่ต้องมี Deno ไม่ต้องมี Supabase ไม่ต้องยิง push จริง

```bash
cd supabase/functions/send-reminders/__tests__
npx --yes esbuild@0.23.1 --bundle --format=esm "--external:npm:*" "--external:jsr:*" \
  --outfile=fn.mjs ../index.ts
node -e "const fs=require('fs');const s=fs.readFileSync('fn.mjs','utf8');fs.writeFileSync('fn.mjs',s.replace('\"npm:web-push@3.6.7\"','\"./wp.mjs\"').replace('\"jsr:@supabase/supabase-js@2\"','\"./sb.mjs\"'))"
node run.mjs
```

`fn.mjs` เป็นของที่สร้างใหม่ได้ตลอด จึงอยู่ใน `.gitignore` —
**สร้างใหม่ทุกครั้งที่แก้ `index.ts`** ไม่งั้นเทสต์จะผ่านกับโค้ดรุ่นเก่า

## ทำไมต้องมี

ไฟล์นี้เป็นที่เดียวในระบบที่ตัดสินใจว่า "ใครควรได้รับการแจ้งเตือนอะไร เมื่อไหร่"
และเป็นโค้ดที่ **ทดสอบด้วยมือแทบไม่ได้เลย** — เงื่อนไขส่วนใหญ่ขึ้นกับเวลาจริง
(กลางคืน · ช่วงเย็น · ช่องว่าง 25 นาที · เพดานต่อวัน) กับสภาพข้อมูลที่จัดให้เกิดยาก
(subscription หมดอายุ · ตารางที่ยังไม่ได้ deploy · ข้อความ 5 ข้อความในห้องเดียว)

บั๊กของไฟล์นี้ยังเป็นบั๊กชนิดที่ **เงียบ** ด้วย: คนที่ไม่ได้รับการแจ้งเตือน
ไม่มีทางรู้ว่าตัวเองไม่ได้รับ และไม่มีอะไรบนหน้าจอฟ้อง กว่าจะรู้ก็คือตอนที่เขา
พลาดงานส่งไปแล้ว หรือตอนที่เขาเลิกใช้แอปไปเงียบ ๆ

## สิ่งที่ของจำลองครอบคลุม

`stubs.js` ทำ query builder ของ supabase-js **เฉพาะรูปที่ `index.ts` ใช้จริง**
ไม่ได้พยายามทำให้ครบทั้งไลบรารี — เพิ่มคิวรีรูปใหม่ในฟังก์ชันเมื่อไหร่ ต้องมาเพิ่มที่นี่ด้วย

⚠️ กับดักสองข้อที่เคยทำให้เทสต์ "ผ่าน/ตก" ผิดมาแล้ว และแก้ไปแล้ว — อย่าเผลอทำซ้ำ:

1. **`createClient()` ถูกเรียกครั้งเดียว** ตอน `ensureInit()` แล้วฟังก์ชันถือ reference นั้น
   ไว้ตลอดอายุ instance · `__setTables()` จึงต้อง **แก้ไส้ในก้อนเดิม** ไม่ใช่สลับก้อนใหม่
   ไม่งั้นเทสต์ตัวที่สองเป็นต้นไปจะอ่านข้อมูลของเทสต์ตัวแรก แล้วตกแบบอธิบายไม่ได้
2. **`.delete()` ต้องลบในอาร์เรย์เดิม** (`length = 0` แล้ว push กลับ) ไม่ใช่ `tables[x] = ใหม่`
   เพราะเทสต์ถือ reference ของอาร์เรย์เดิมไว้ตรวจผล
